# Integrated Visualizer 運用・移行方針

方針確定日: 2026-09-20  
最終更新日: 2026-09-21

## 決定事項

各個別可視化ページは、EnvGeo-Seawaterの正式な主要ワークフローとして残します。
アップロードデータの検証と既存データとの比較は、独立したUser Data Validatorページへ移します。
Integrated Visualizerは移行中のbeta試験基盤とし、必要な機能の移行完了後は非公開の開発アーカイブにします。

アップロード機能の実装は1つに共通化します。共通処理とUIは、
`envgeo_utils.py` をさらに巨大化させるのではなく、仮称 `envgeo_user_data.py` のような
専用コアモジュールへ切り出します。

## この方針を選ぶ理由

T-S図、水深プロファイル、地図、鉛直断面、Custom plotでは、必要列、科学的な品質確認、
図の設定が異なります。描画処理を目的ごとのページに残すことで、挙動の理解、テスト、
文書化、科学的な変更のレビューが容易になります。すべてを1ページに集約すると、依存関係が強くなり、
保守が難しくなります。

独立したUser Data Validatorで品質確認と既存データとの簡易比較を行うことで、
論文図向けの詳細設定と検証操作を混在させずに済みます。検証したデータはセッションで保持し、
必要な個別ページへ引き継ぎます。

## 現在の過渡的な構成

- アップロードファイルと前処理済みデータは、現在のStreamlitセッション内のメモリだけで保持します。
- CSV/Excel読み込み、列名標準化、数値化、海水品質ルール、d-excess計算、セッション共有は `envgeo_utils.py` が担当します。
- 共通のアップロード、列対応、マーカー設定パネルは `envgeo_user_data.py` が提供し、T-S DiagramとSalinity-d18O Relationshipから利用します。
- T-S DiagramとSalinity-d18O Relationshipのページ側には、その図の必須列定義とMatplotlib重ね描画だけを残します。
- Integrated Visualizerも同じ共通前処理とセッションデータを使いますが、別のStreamlit UIとPlotly重ね描画を持っています。
- Integrated Visualizer内でT-S Diagramを開く場合は、Integrated側がファイル読み込み、T-S側がマーカー設定と重ね描画を担当し、UIの重複と二重描画を防いでいます。
- その他のFull existing pageは、個別ページ側の重ね描画が完成するまで、一時的なデータ読み込み関数の差し替えを使っています。
- Shared-filter betaが現在担当している検証・比較機能は、独立したUser Data Validatorへ移します。

この責務分担は移行中の形であり、最終構成ではありません。

## 最終的な責務分担

| 層 | 担当 |
| --- | --- |
| 共通アップロードコア | メモリ上のファイル読み込み、列対応、手動列修正、数値化、検証結果、品質フラグ、派生値、セッション保持 |
| 海水用アップロードルール | 海水の別名列、必須列プロファイル、有効範囲、d-excess設定 |
| 共通Streamlit UI | アップロード、テンプレート、認識列レポート、手動修正、品質概要、クリア操作、共通マーカー設定モデル |
| User Data Validator | 列対応の確認・修正、品質レポート、除外理由、既存データとの比較、簡易診断図 |
| 個別ページ | その図の必要列、除外数概要、描画ライブラリ用の変換、最終的な重ね描画 |
| Integrated Visualizer | 移行中の試験基盤。移行完了後は非公開の開発アーカイブ |

マーカー設定は、サイズ倍率、固定色または共通カラーバー、形、透明度、輪郭色、輪郭幅を持つ、
描画ライブラリに依存しない共通モデルとします。個別ページはそれをMatplotlibまたはPlotlyの引数へ変換する部分だけを担当します。

## 最終的なユーザーデータ運用フロー

1. 対象となる各個別ページは、サイドバー上部に共通アップロードパネルを配置し、前処理済みデータを同じメモリ内セッションへ登録する。
2. 個別ページは、簡潔な品質概要、その図に必要なマーカー設定、ページ固有の重ね描画を担当する。詳細な検証画面は重複実装しない。
3. User Data Validatorは、どの個別ページからアップロードされたデータでも同じセッションから開ける。列対応、欠損値・範囲外値、品質フラグ、除外件数と理由、既存データとの比較、必要に応じた品質レポート出力を詳しく確認できるようにする。
4. 品質基準と派生値計算はValidatorページ内ではなく共通コアへ実装する。これにより、同じアップロードデータに対して、個別ページとValidatorが同じ判定結果を表示する。
5. 対象ページのいずれかがIntegrated側のアップロードに依存している間は、Integrated Visualizerのアップローダーを残す。全対象ページで個別アップロード・重ね描画を確認し、独立ValidatorでShared-filter相当の品質確認ができた段階でのみ、Integratedのアップローダーを廃止する。

アップロードデータは現在のStreamlitセッション内だけで利用し、ローカルまたはサーバーへ保存しない。

## 列対応UI

個別ページのアップロード関連UIは、サイドバー上部へ `Uploaded data overlay`、
`Uploaded data columns`、`Uploaded marker style` の順に3つの折りたたみパネルを配置する。
既知の別名は自動対応し、その結果も変更可能な選択欄として表示する。未知の列名は推測だけで
採用せず、ユーザーが描画上の役割を明示的に選ぶまで未設定とする。

科学的な目的が決まっているページでは、単なるX・Yではなく `Temperature column`、
`Salinity column` のように意味を示す。汎用Custom VisualizerではX、Y、Z、Colorの役割を
選択できるようにする。役割を割り当てても元の列は残し、新規元素や試験的パラメーターを
後のCustom plotで利用できるようにする。必須の役割が不足する場合は列対応パネルを自動的に開き、
対応が完了するまで重ね描画しない。

採水地点地図を持つ個別ページでは、主図だけでなく地図にもアップロード対応を実装する。
有効な経度・緯度を持つ行を、区別しやすい輪郭付きマーカーで最前面に描画し、地図の自動表示範囲にも含める。
既存地図の色分け列と互換性がある場合は同じカラースケールを使い、色値がない行は固定アップロード色へ戻す。
位置列がない、または無効な場合は地図へ表示できない理由と、表示・除外件数を明記する。

## User Data Validatorへ移す機能

- 地図や関連図を共通フィルターで探索する機能。
- アップロードデータの品質確認と簡易可視化。
- 認識された列名の報告と将来の手動列修正。
- 除外件数と理由の表示。
- 既存データとの簡易比較。
- セッションを通じた個別ページへのデータ引き継ぎ。

## 個別ページ対応後に廃止する機能

- Integrated専用のアップロード前処理。
- `load_isotope_data` の一時的なモンキーパッチ。
- 互換性確保のためのFull existing page方式。
- Validator側の対応確認後の、T-S図、塩分-d18O図などの重複した検証実装。

Integrated Visualizerのソースは開発アーカイブとして残すことができますが、
移行完了後は通常の公開ワークフローとして提示しません。

## 移行順序

1. アップロード処理、共通UI、セッション保持、品質レポート、必須列プロファイル、マーカー設定モデルを専用コアモジュールへ切り出す。
2. T-S Diagramのページ内UIを共通部品で置き換え、再テストする。2026-09-21完了。
3. Shared-filter betaを独立したUser Data Validatorページへ移す。
4. Salinity-d18O Relationship、Mapping、Depth Profile、Custom Parameter Plot、Interactive 2D/3D/4D、Vertical Sectionへ小さな単位で展開する。Salinity-d18O Relationshipは2026-09-21完了、その他は未実装。
5. 個別ページの重ね描画確認後、そのページをIntegratedの一時ローダー差し替え対象から外す。
6. Validatorと個別ページへの移行完了後、Integrated Visualizerを通常の公開ページ一覧から外す。

各段階で、対象を絞ったpytestとAppTestまたは画面確認を行ってから次のページへ進みます。

## 一度に変えないための移行原則

- 1回の作業は「共通部品の追加」または「個別ページ1つの導入」に限定する。
- 新実装のテストと画面確認が完了するまで、現行のIntegrated機能を削除しない。
- ValidatorがShared-filter betaと同等の検証を行えるまで、Shared-filter betaを残す。
- 対象の個別ページが完了するまで、そのFull existing page経路を残す。
- 各段階の完了時点で、作業を一時停止しても現行アプリを利用できる状態を保つ。

## 将来のenvgeo4d構成

- 現在の移行段階: アップロード処理と共通UIは、すべてを `envgeo_utils.py` へ追加せず、`envgeo_user_data.py` のような専用モジュールで管理する。
- `envgeo4d/common`: ファイル入力、セッション保持、列対応枠組み、検証結果構造、共通UIモデル。
- `envgeo4d/seawater`: 海水の別名列、有効範囲、d-excess、図ごとの必要列。
- `envgeo4d/earthquake` および将来の分野: 共通基盤を使いつつ、分野固有のスキーマと品質ルールを持つ。

未知の列名を推測だけで確定してはいけません。自動認識後に列対応結果を表示し、
必要な場合はユーザーが明示的に修正できる構成にします。
