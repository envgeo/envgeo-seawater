# コード案内

EnvGeo-Seawaterのソース構成を、開発者・レビュー担当者向けに短く示す案内です。各ファイルの役割と変更時の境界を説明するものであり、APIリファレンス、コード内docstring、利用者マニュアルの代わりではありません。

[English version](code_guide.md)

配布基盤については
[`distribution_foundation_audit_and_plan_Japanese.md`](distribution_foundation_audit_and_plan_Japanese.md)を参照してください。

## 中心モジュール

| ファイル | 役割 | 変更時の注意 |
|---|---|---|
| `home.py` | Streamlitの入口。概要、引用、manual、更新履歴などのHomeタブを表示する。 | 現在のローカル／Cloudの起動先である。入口移行を計画するまで`streamlit run home.py`を維持する。 |
| `envgeo_assets.py` | 起動時のカレントディレクトリに依存せず、読み取り専用の同梱資産をアプリルートから解決する。 | 同梱資産には`asset_path()`を使う。個人データ、出力、将来の書込み可能キャッシュには使わない。 |
| `envgeo_launcher.py` | `envgeo-seawater`でインストール済みアプリを起動するコンソール入口。 | 呼出元のカレントディレクトリに依存しない起動経路を維持する。 |
| `envgeo_diagnostic_launcher.py` | `envgeo-seawater-check`でローカル診断ツールを起動するコンソール入口。 | 診断機能を通常の公開Streamlitナビゲーションに入れない。 |
| `envgeo_utils.py` | データ読込、正規化、品質チェック、フィルター、地図スタイル、海岸線、共通エクスポートを扱う。 | 広い既存共通基盤である。無関係な一括リファクタリングを避け、対象を絞りテストする。 |
| `envgeo_user_data.py` | ブラウザ内だけのアップロード、列の標準化、品質フィードバック、アップロード記号を扱う。 | ブラウザアップロードを無断で保存・公開参照データへ混合してはいけない。 |

## データ・資産ディレクトリ

| ディレクトリ | 内容とルール |
|---|---|
| `dataset/` | 公開参照workbook。専用のデータ／来歴レビューなしにコピー、削除、移動、変更しない。 |
| `local_data/` | Git管理するゼロ値公開`user_data.xlsx`サンプルと英日説明。研究者個人データは外部ファイルを指定するか、公開同期前にゼロ値サンプルへ戻す。 |
| `coastline/` | オフライン海岸線CSV、Natural Earth 50m陸域、来歴情報。 |
| `bathymetry/` | 派生GEBCO格子と、ソースにのみ残す生成補助。Page 53が読むのは格子だけであり、生成補助はwheelから除外する。 |
| `data/`・`data_text/` | デモメディア、アプリ内テキスト、引用、manual、更新ログ。 |
| `docs/` | 開発判断、科学計画、リリース記録、英日文書。 |
| `test/` | pytest回帰テスト。挙動変更ごとに焦点テストを追加する。 |

## 文書化の目安

- 再利用するモジュールや公開ヘルパーには、目的・入出力・重要な安全境界を短いdocstringで書く。
- コメントは、明白でない意図、科学的仮定、互換性上の制約にだけ使う。自明な代入を全て日本語・英語で言い換えない。
- 設定値、データ構造、関連する補助関数の境目には、役割を示す英日併記の見出しを置く。短い代入や各`def`ごとに
  増やすのではなく、意味のある機能群を小数の見出しで区切る。
- 長い解説、データ来歴、ワークフロー判断、英日案内はページスクリプトではなく`docs/`へ置く。
- 利用者、再現性、公開上の主張、科学的解釈に影響する判断は、英日両方の記録を揃える。

## コードコメントと書式の統一基準

以下を、稼働中の共通コードと安定版ページに適用する。手書き開発履歴として残すPage 80は、
必要な機能・安全性・配布上の修正以外は対象外とする。

```python
# =============================================================================
# Major role-based section / 主要な役割区分
# =============================================================================

# -------------------------------------------------------------------
# Related subgroup / 関連する下位区分
# -------------------------------------------------------------------
```

- 設定、データ読込、地図スタイル、レポートなどのモジュールレベルの区分には`=`形式を使う。長い関数内の
  関連する下位区分・一貫した処理段階には`-`形式を使う。
- 英語を先、日本語を後に置く。変更履歴ではなく役割・理由を書くため、「修正済み」、日付、一時的な開発メモは残さない。
- 大見出しに通し番号は付けない。一つの複雑な処理手順を分かりやすくする短い手順番号は使用できる。
- 科学的仮定、欠損値・gap row保持、互換性制約、来歴の境界、明白でない安全処理の説明は残す。
  未使用と確認したdebug出力、旧いコメントアウトコード、重複した実装例は削除する。
- 自明な代入にはコメントを付けない。長い根拠、判断、利用者向け説明は`docs/`へ置く。
- 可能な限り書式だけの変更と挙動変更を分け、リスクに応じた構文確認と焦点テストを行う。

## コード変更前の確認

1. 関連manual、更新ログ、`docs/`内の計画、`TODO.md`を読む。
2. `dataset/`、公開／非公開データ境界、既存の共通フィルターを守る。
3. 焦点テストを追加または更新し、アプリルートから適切なpytestを実行する。
4. 重要変更は英日更新ログへ記録する。Codexはcommit/pushを行わず、公開クローン同期はGitHub Desktopで確認する。
